# WhatsNewDock v0.1.3

**Update checking is honest again** — and updating WhatsNewDock now takes your
agents with it.

Everything from [v0.1.2](https://github.com/TheRealChickenLegs/WhatsNewDock/releases/tag/v0.1.2)
is still here.

---

## "Check now" now shows what it finds

A container pinned to a partial version could sit silent forever. `nginx:1.25`
was treated as a moving tag, so it was only compared against the digest of the
tag itself: the digest matched, and WhatsNewDock reported nothing while Docker
Hub had 1.31 waiting.

Version pins are now compared against the release list, at the precision you
pinned:

- **`1.25`** moves when a newer version *line* exists — 1.30, 1.31. A same-line
  patch is left to the digest, because the container already tracks that moving
  tag, and reporting it every time would be noise.
- **`1.25.3`** moves for any newer release.
- **The variant is kept.** `1.25-alpine` is offered the next alpine build, never
  the Debian one, and `1.25-alpine3.20` is never offered a `-slim`.

Two more fixes came out of the same investigation:

- **"Check now" could finish without doing anything.** The check inherited the
  request context, which the HTTP server cancels the moment the response is
  written — so the check was aborted before it looked anything up. It now runs
  on a context of its own, and a check that *is* cancelled is reported as a
  failure rather than looking like a check that simply found nothing.
- **The button waits and tells you the result** — "Check complete — 3 updates
  available" — instead of stopping its spinner after a second while the check
  was still running behind it.

Variant tags such as `alpine3.24` are no longer read as version 3.24.0 either,
which could make them outrank a real release as the suggested update target.

## Updating WhatsNewDock updates your agents first

If you monitor other hosts with agents, **Update now** is now a sequence rather
than a single action:

1. Every reachable agent is moved onto the new version.
2. Only once they are all back is this controller replaced.

The card lists each agent and the phase it is in. An agent that fails, or that
does not report back within three minutes, stops the run and **leaves this
controller alone** — a deployment is never left split across two versions.
Offline agents are listed as skipped. Fix or remove the agent, then press
**Update now** again.

The **Servers** page shows the build each agent is running: green when it matches
this controller's version, red when it is behind.

One caveat: an agent running as a Swarm service, or in any runtime where it
cannot recreate its own container, reports that it could not self-update. The
controller then stays put, and you update that agent from its host — for a Swarm
service, `docker service update --force <service>`.

## Also in this release

- **Quieter agent logs.** A graceful restart (SIGTERM) is logged as a restart and
  exits 0, instead of being reported as an ERROR with exit code 1. A transient
  502 from the socket proxy is summarised as a warning rather than dumping the
  proxy's HTML error page into the log.
- **A self-update run that stopped short explains itself** in the sidebar card,
  naming the agents that did not come back, instead of the reason only being
  visible in Events.

## Container image

Multi-arch (`linux/amd64`, `linux/arm64`), published to GHCR:

```bash
docker pull ghcr.io/therealchickenlegs/whatsnewdock:0.1.3   # or :latest
```

Because this is a 0.1.x release, configuration flags and the on-disk database
schema may still change between minor versions. Back up the data directory
before upgrading.
