# WhatsNewDock v0.1.2

**WhatsNewDock now updates itself** — and can tell you when a rebuilt image, not
just a new release, is waiting.

Everything from [v0.1.1](https://github.com/TheRealChickenLegs/WhatsNewDock/releases/tag/v0.1.1)
is still here.

---

## WhatsNewDock watches its own releases

A card at the base of the sidebar tells you when there is something newer to
run, and can redeploy the app for you:

- **On by default**, checked every 24 hours. Both are configurable in
  **Settings → WhatsNewDock self-update**, or with `WND_SELF_UPDATE` and
  `WND_SELF_UPDATE_INTERVAL`.
- The check only reads this repository's published releases. Nothing is
  downloaded until you press Update.
- The card shows the version pair and the release notes, and **Update now**
  (admins) redeploys in place: same container name, ports, volumes and settings.
  The page reloads itself once the new version answers.

It detects two different things, and says which:

- **A newer release** — `v0.1.1 → v0.1.2`. The update moves the container to that
  release tag.
- **A rebuilt tag** — `:latest` has moved. A moving tag keeps the same version
  string forever, so this compares the digest you are running against the digest
  the registry now serves for the *same* reference, and re-pulls that same tag.
  It can never move you backwards.

A container cannot recreate itself, so the work is handed to a short-lived
helper container started from the image already running on the host. It replaces
this container and exits. It is given exactly the Docker access this container
has and nothing more, and never receives the data volume.

Two things to know:

- **If you pin a release tag** (`:0.1.1`) and self-update, the running container
  is moved to `:v0.1.2`. Update the tag in your compose file too, or a later
  `docker compose up -d` will put the old version back.
- **If the app cannot identify or reach its own container**, the card says so and
  shows the command to run by hand instead.

### Main builds now say which build they are

An image built from `main` used to report its version as the string `main`,
which meant nothing in the About page or the logs — and it was why the update
check could not reason about a `:latest` deployment at all. Builds now carry a
`git describe` version such as `v0.1.1-3-gabc1234`.

## Also in this release

- **Filter stacks by server** — the Stacks page lists every Compose project and
  Swarm stack across all hosts, and can now be narrowed to one, with a count
  that names the filter.
- **Fixed a doubled `v` on the About page** — releases displayed `vv0.1.1`. The
  version is now shown as built: a tag stays `v0.1.1`, a branch build says
  `main`, a local build says `dev`.
- **Swarm updates stay opt-in.** Unchanged from v0.1.1: monitoring needs no extra
  permission, rolling a service needs `SERVICES=1` on the socket proxy.

## Container image

Multi-arch (`linux/amd64`, `linux/arm64`), published to GHCR:

```bash
docker pull ghcr.io/therealchickenlegs/whatsnewdock:0.1.2   # or :latest
```

Because this is a 0.1.x release, configuration flags and the on-disk database
schema may still change between minor versions. Back up the data directory
before upgrading.
