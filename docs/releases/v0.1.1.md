# WhatsNewDock v0.1.1

**Docker Swarm support**, and swarm is a first-class citizen rather than a host
that happens to have containers on it.

Everything from [v0.1.0](https://github.com/TheRealChickenLegs/WhatsNewDock/releases/tag/v0.1.0)
is still here — this release adds Swarm handling and leaves standalone Docker,
Compose and Podman exactly as they were.

---

## What's new

### Swarm hosts are monitored out of the box

Task containers carry swarm's own labels, so what WhatsNewDock already reads is
enough to understand them. No extra permission, no configuration:

- **Stack → service → task**, the way you actually think about a swarm. The
  Stacks page now lists each stack's services with a running/total task count.
- Service names on every task, with the node and task id in the detail view.
- Update availability is per task, as before, and rolls up to the service.

### Updating a service is opt-in

A swarm task belongs to a service, so **it is never recreated directly**. The
orchestrator owns it: stopping one makes swarm schedule a replacement, and a
container we created would carry another task's labels. Instead the update is
handed to swarm, which rolls every replica.

That needs the services API, so it stays off unless you ask for it:

```yaml
  socket-proxy:
    environment:
      SERVICES: "1"   # was "0"
      POST: "1"       # already required for updates
```

Restart the proxy and WhatsNewDock, and a manager node's update button starts
rolling services. Until then the UI says so plainly on the server page, and a
worker node is told to use a manager rather than failing halfway. `/services`
returns full service definitions — environment variables, secret names,
registry configuration — so this is a deliberate, documented widening of the
proxy's surface; see [`docs/SECURITY.md`](https://github.com/TheRealChickenLegs/WhatsNewDock/blob/main/docs/SECURITY.md).

### A rollout that goes wrong is undone

Updating a service:

1. pulls the new image — a failed pull leaves the service untouched;
2. re-queries the registry, so a floating tag picks up its new digest;
3. bumps the force counter when the image reference has not changed at all,
   because otherwise swarm sees an identical spec and rolls nothing out;
4. waits for the orchestrator to report the rollout **completed** with every
   desired task running, and only then reports success.

A rollout that never settles is rolled back to the previous spec and reported as
a failure, so a crash-looping image is never mistaken for a good update.

Judging that correctly turned out to be the subtle part, and only a real daemon
showed it: `ServiceInspect` does not populate task counts at all, and during a
rolling update `running == desired` is true the entire time the old version is
still serving. Trusting either would have reported success while nothing had
changed. Convergence now requires the daemon to say the rollout is complete.

## Notes

- **Swarm updates need an up-to-date agent.** An older agent does not recognise
  swarm labels and would fall back to recreating a task container, so update the
  agent on any swarm host before using the feature.
- The host must be a **manager**; workers can be monitored but not updated.
- CI now runs a live swarm test on every push: a throwaway single-node swarm,
  a real service update, a forced roll and a rollback, cleaned up afterwards.

## Container image

Multi-arch (`linux/amd64`, `linux/arm64`), published to GHCR:

```bash
docker pull ghcr.io/therealchickenlegs/whatsnewdock:0.1.1   # or :latest
```

Because this is a 0.1.x release, configuration flags and the on-disk database
schema may still change between minor versions. Back up the data directory
before upgrading.
